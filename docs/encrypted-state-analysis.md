# 加密状态、无状态计算与去中心化：设计审查

状态：研究与设计建议，2026-09-16；未实现加密协议。本文补充[主设计](stateful-api-design.md)，讨论威胁模型与工程取舍，不构成密码协议安全证明或专利新颖性检索。

## 1. 结论

用户提出的“全量状态加密交给客户端，每人只解密自己能看的部分”**可以实现**，适合可移植检查点、可信调度器持有的训练分支和跨机器迁移。但是它单独解决不了回滚、分叉、并发、重连恢复和评测作弊。

本项目建议分为三个层次：

1. **规则内核无状态**：`nextState = transition(state, action, context)`，执行确定性规则，不依赖 HTTP、数据库或加密方案。
2. **在线对局有状态**：每局一个权威更新入口，原子提交当前状态、事件和幂等回执；按玩家生成观察。
3. **训练可显式分叉**：可信调度器可导出加密检查点并批量执行，分支必须有父局与实验用途标记，不能充当未经回退的正式评测。

**Serverless 不要求应用没有状态。** 例如 Cloudflare Durable Objects 将带持久存储的单个对象作为协作会话的协调点；不同对象可并行运行。按 `episodeId` 分配对象就能横向扩展大量对局，而不必让同一局的相冲突动作同时成功。[Cloudflare 官方说明](https://developers.cloudflare.com/durable-objects/concepts/what-are-durable-objects/)

## 2. 先区分四种不同的目标

| 目标 | 用户方案能否单独做到 | 所需机制 |
|---|---|---|
| 玩家不能看到别人的手牌 | 可以，但要正确分区及管理密钥 | 玩家观察过滤；必要时独立密文 |
| 玩家不能篡改权威状态 | 可以，但玩家不能持有权威认证密钥 | 服务端独占的 AEAD 密钥或服务端签名 |
| 同一局始终只有一个已提交的下一状态 | 不能 | 记住当前版本/状态摘要的原子更新入口，或参与者共识 |
| 服务商也不知道任何玩家手牌 | 普通服务端加密封装不能做到 | 去信任发牌、可验证洗牌、选择性解密，必要时 MPC/ZK |

这四个目标分别是**保密、完整性、一致性、减少对服务商的信任**。是否保存状态、是否采用区块链、是否可 serverless 部署，是另外的工程选择。将它们合并成一个“去中心化”开关容易掩盖问题。

对于 agent 训练，首先需要的是规则正确、玩家之间的信息隔离和轨迹可信；通常可以信任环境运行器。对服务商也隐藏所有牌，属于更强的另一种威胁模型。

## 3. 真的采用加密状态包，应怎样分层

### 3.1 服务端权威包与玩家观察分开

概念结构如下，字段不是已实现 API：

```ts
interface StateCapsule {
  protocolVersion: string;
  keyId: string;
  nonce: string;
  ciphertext: string; // 全量 canonical state，包含私有牌序与 RNG 状态
  tag: string;
}

interface PlayerResponse {
  observation: PlayerObservation;
  capsule?: StateCapsule; // 仅可信协调器或指定载体接收；不放入模型上下文
}
```

全量真实状态由服务端封装，玩家不持有它的解密/认证密钥。服务端校验并解密包，执行规则，再重新生成该玩家的观察。规则引擎读取真实状态，不能把客户端提交的“自己的手牌分区”当作事实。

在 TLS 和正常认证之上，通常直接给玩家其有权看到的观察即可。把所有人的私有密文也下发，会增加带宽、密钥管理和侧信道；对可信服务端模式没有必然收益。若需要离线转交观察，才另做收件人专用的加密观察包。

AEAD 同时提供密文完整性与保密，附加认证数据 AAD 可以绑定协议、对局、用途等上下文；它自身不负责防重放或授权。只有签名的 JSON 仍可阅读，不适合存放隐藏手牌。[RFC 5116，§1.2 与 §2](https://www.rfc-editor.org/rfc/rfc5116.html#section-1.2)

### 3.2 两个容易误用的密码概念

- **JWE 多收件人并不等于字段级权限。** 它通常让多个收件人解开同一份明文。要让 P1 看手牌 A、P2 看手牌 B，应分别封装两份内容；不能给同一个全状态 JWE 添加多个 recipient 后期待自动隐藏不同字段。[RFC 7516，§1、§7.2](https://www.rfc-editor.org/rfc/rfc7516.html#section-7.2)
- **可以解密不代表只能读取。** 若玩家持有某分区的对称 AEAD 密钥，也能生成该分区的有效密文；所以它不能成为服务器接受的权威状态。若任意人都能用服务器公钥创建 JWE，这同样不证明状态由服务器签发。应由服务端独占认证密钥封装，或让服务器签名覆盖整个受保护包与上下文。

这些是协议设计约束，不是选择一个加密库就会自动获得的属性。

### 3.3 必须绑定的上下文

权威包的受保护内容至少绑定：`tenantId`、`episodeId`、`branchId`、规则/组件/序列化版本、状态代数、用途、有效期与权限版本。某些字段自身可能泄露信息，应放入密文而非明文 AAD。不要公开秘密同时提交产生的真实内部版本。

解密后仍要做运行时 schema 校验、大小/深度限制、固定算法白名单、密钥用途检查、对局归属及动作授权。跨局粘贴、跨租户粘贴、旧规则包和把训练分支包送进正式评测，都应拒绝。

随机数与加密 nonce 是不同用途的随机量。模拟所需的可重放 RNG 状态不能直接复用作加密 nonce；分叉时更不能按 `episodeVersion` 生成相同 key 下重复 nonce。GCM 的 nonce 重用会破坏安全属性。[RFC 5116，§5.1.1](https://www.rfc-editor.org/rfc/rfc5116.html#section-5.1.1)

## 4. 为什么完整性保护阻止不了回滚与分叉

设客户端持有服务器合法签发的第 17 步状态包 `C17`，向两个临时计算实例发送：

```text
请求 A：C17 + 出牌 a  → C18a
请求 B：C17 + 出牌 b  → C18b
```

两个请求的输入包都真实、未篡改，动作也可能都合法。如果实例没有共享的当前 head、已消费记录或其他共识状态，它们看到的证据都与“这是第一个请求”相同，因此可以同时签发两个后继状态。之后客户端可以保留对自己更有利的一条分支。

**在允许客户端保存旧包、可发送两个不同合法后继请求、且验证方没有可变共享记录或外部唯一性来源的假设下，不能保证全局只有一个当前分支。** 这是上述反例的推论，不是声称所有特殊场景都必须使用数据库。

- 签名、版本号和前一状态哈希可以证明“来自某个合法旧状态”，不能证明“没有别的后继”。
- `expiresAt` 只缩短旧包可用时间；有效期内仍可同时提交两条分支。
- 幂等 key 若没有消费记录，只是客户端提交的一段字符串。
- 完整哈希链能检查收到的链是否自洽，不能单凭一条链知道另一条有效链不存在。
- 让所有玩家共同签字可以减少单方分叉，但他们必须记住已签 head；这是将状态和协调移到了玩家侧，并引入掉线阻塞与恢复问题。

对于隐藏信息评测，允许这种接口会产生额外问题：模型或其工具编排器可以先试探未来，再回到旧包选择动作。密文未被破解，评测却已经失真。检查点和分叉权限必须放在可信调度器侧，而不是被评测策略侧。

### 4.1 保留最小状态的折中

如果目标是减少热存储体积，可以只在权威存储保留：

```text
episodeId -> { internalRevision, currentCapsuleDigest, lifecycle, authEpoch }
(episodeId, seatId, requestId) -> { requestDigest, committedReceipt }
```

计算节点接收完整密文包并计算后继；提交时原子执行 compare-and-swap：只有当前 head 与请求对应时才替换。竞争失败不得把未提交分支的观察、抽牌结果或奖励返回策略端。幂等回执、日志/outbox 与 head 更新须在同一事务边界内，或有明确可恢复的提交协议。

这叫**计算层无状态、协调层保存少量状态**。它可以减少数据库的状态读写体积，但仍需保存幂等回执及训练审计资料；所以总成本必须与直接存小型 JSON 状态比较，不能预设它更省。

如果只存摘要、把唯一完整包留在客户端，客户端丢失包或离线就无法恢复。若增加对象存储保存完整包，系统再次拥有了持久状态，只是位置和访问方式不同。这是合理的冷热分层，而不是问题被加密消除了。

## 5. 漏洞与故障清单

以下为本项目的威胁分析与测试建议，并非声称已发现现有实现的漏洞。

| 问题 | 具体失败方式 | 推荐约束/验证 |
|---|---|---|
| 回滚、分叉 | 同一包先试两种动作，再挑胜率高的结果 | 正式评测只允许原子推进当前 head；分叉独立命名与授权 |
| 并发和重试 | 两次成功出同一张牌；超时重试再次扣资源 | 原子 head 更新；同身份幂等 key 与请求摘要绑定 |
| 未提交结果泄露 | 冲突失败却返回先计算出的秘密抽牌 | 只在提交成功后发布观察；失败不含中间结果 |
| 仅加密未证明来源 | 攻击者用服务器公钥加密自造的高分状态 | 独立服务端认证/签名；不接受“能解密即可信” |
| 分区可伪造 | 玩家拿自己的 AEAD key 改手牌 | 客户端观察包不是权威输入；权威封装 key 不给玩家 |
| 密文拼接 | P1 用另一局较好的手牌包替换当前分区 | 绑定租户、局、分支、代数、用途；整体认证 |
| nonce 重复 | 同版本分叉或多实例重用相同 nonce | 使用审查过的库和 nonce 管理；加密随机与模拟 RNG 隔离 |
| 可见性侧信道 | 密文长度、提交版本、HTTP 响应差异暴露对手动作 | 玩家观察投影统一；必要时固定长度/批次发布；不公开内部版本 |
| 低熵摘要 | 明文手牌哈希可通过枚举几十种可能破解 | 不公开裸秘密状态摘要；使用私有认证摘要或带高熵隐藏盐的承诺 |
| 随机数操控 | 请求重试得到新的随机结果；故意非法动作推进 RNG | 确定性转移与已提交随机记录；拒绝动作不消费 RNG |
| 串谋 | 玩家把已解密手牌或密钥发给同伴 | 加密无法阻止授权接收者主动分享；依靠进程/凭证/通信隔离与研究协议 |
| 撤销无效 | 已离队者仍用旧密钥读取先前存下的密文 | 新数据换 key/权限版本；已获知内容不能“收回”；快速撤销需可变记录 |
| 客户端丢状态 | 唯一密文包丢失或客户端停止转发 | 持久检查点或可信协调器；定义恢复窗口与过期行为 |
| 规则版本漂移 | 新引擎解读旧包，静默改变合法动作/得分 | 固定适配器和组件摘要；显式迁移或拒绝，不自动升级进行中的局 |
| 审计不完整 | 客户端只上传获胜分支 | 可信调度器登记所有运行；保存提交事件、观察和失败/截断记录 |
| 过量输入 | 超大加密包耗尽解密/解压/解析资源 | 限制包体、解压后大小、对象深度与请求频率 |

## 6. 公平随机与去中心化要额外解决什么

### 6.1 当前训练服务：信任环境运行器

服务端使用私有种子、确定性 RNG、不可变规则版本，记录实际发生的随机结果以供回放。可以在开局登记种子/牌序的带隐藏盐承诺，在允许的终局或独立审计阶段验证；不能为了公开可验证而提前公开未来牌序。

承诺证明“没有在之后改这个已承诺的值”，不证明种子最初无偏。多方 commit–reveal 能减少单方选种子，但最后揭示者可能选择中止不利对局，因此还需超时、中止统计及公平性定义。不要把“可重放”“已承诺”“无偏”“运营方不知道牌”视为同一性质。

### 6.2 真正减少对发牌服务器的信任

密码学中已有 **mental poker**：参与者在不依赖可信发牌人的条件下实现隐藏牌、洗牌与分发。Shamir、Rivest、Adleman 的工作已存在多年，作者托管的论文可直接查阅。[原始论文](https://people.csail.mit.edu/rivest/pubs/SRA81.pdf)

可参考的开源实现：

| 项目 | 机制与范围 | 对本项目的意义 |
|---|---|---|
| [LibTMCG](https://www.nongnu.org/libtmcg/) | C++ mental poker 工具，使用零知识证明；GPL-2.0 或后续版本；文档明确讨论至少一位诚实玩家及玩家主动分享手牌的边界 | 证明没有中央可信发牌人的卡牌协议已有实现；不是现成十款合作桌游环境 |
| [Geometry mental-poker](https://github.com/geometryxyz/mental-poker) | 基于 Barnett–Smart 卡牌协议与 Bayer–Groth 可验证洗牌的 Rust 库 | 可研究隐藏、洗牌与选择性揭示；采用前仍需逐项核验许可、维护、安全审计和游戏规则覆盖 |
| [zkShuffle](https://zkholdem.xyz/wp-content/themes/zkholdem-theme/zkshuffle.pdf) | 描述链上加密牌堆、证明洗牌和部分解密的方案 | 展示区块链承担公开协调/验证；链上仍保存状态，不是让状态消失 |

洗牌和出牌正确，不自动证明复杂合作游戏的全部规则都正确。例如“必须跟某花色”“不能说出秘密数字”“战役奖励的合法来源”可能还需要额外证明、可验证执行或受信引擎。密码协议也不会替代适配器的官方规则测试。

区块链会将排序、共识与数据保存交给一组节点。选择它的理由应是参与者不愿信任单个权威，而不是“serverless 需要它”。对于自己的 RLVR/SFT 训练平台，按对局划分的权威服务通常更简单，且更易复现；这是本项目的工程判断。

## 7. Redis、SQL、actor 与状态包的取舍

| 方案 | 推荐场景 | 优点 | 主要代价 |
|---|---|---|---|
| 单进程本地内存 | 可信批量训练 worker | 无网络往返；每个 worker 管自己的独立局 | 崩溃恢复依赖周期检查点；不能用于多实例共享同一局 |
| SQLite / PostgreSQL 权威状态 | 首版研发、在线评测与可靠审计 | 状态、幂等回执、事件可原子提交；调试直接 | 需管理数据库容量、索引和备份 |
| 每局一个持久 actor | serverless 多人游戏服务 | 同一局集中协调，跨局并行；状态与计算靠近 | 平台约束；单局热点仍需限制；单线程不免除异步 interleaving 审查 |
| Redis 权威热状态 | 确有低延迟/高更新吞吐需求 | Lua/事务可做单局原子更新，读写快 | 持久化、淘汰、TTL、主从故障恢复与双写需单独设计 |
| 加密包 + 最小 head | 状态很大、计算节点短暂、需搬迁检查点 | 减少状态查询；计算任意调度 | 请求带宽、密钥轮换、完整包恢复、head/日志一致性 |
| 完全无 head 的加密包 | 可信协调器执行的可分叉训练/搜索 | 易搬迁、复制与批量 rollout | 不保证唯一对局历史；不开放给正式评测策略 |
| 多方密码协议 + 共识 | 不信任运营方的公开游戏 | 减少对中央发牌与执行方的信任 | 协议、掉线、性能、证明与规则表达复杂度显著增加 |

Redis 支持通过 `WATCH` 检测并发修改并配合事务提交；持久化可选择 RDB/AOF，但配置和故障窗口影响已确认数据的恢复。故不能简单写成“放 Redis 就保证不丢且可无限扩展”。如 SQL 是最终权威，Redis 优先做缓存、限流或调度；不要未经设计地双写 Redis 状态和 SQL 事件。[Redis 事务](https://redis.io/docs/latest/develop/using-commands/transactions/)、[Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

若采用 Durable Objects，应按对局拆分，避免所有对局共用一个全局对象。官方文档把带强一致协调的回合制游戏列为适用场景；这里选择它仅说明存在可用的有状态 serverless 路线，不代表已经评测本项目的价格或吞吐。[Cloudflare 设计建议](https://developers.cloudflare.com/durable-objects/best-practices/rules-of-durable-objects/)

## 8. 是否创新，以及值得做什么实验

**“加密状态在客户端保存”“每人只读取授权内容”“无中央发牌人的卡牌协议”这些宽泛思想已有明确先例，不能据此主张密码学创新。** 本轮检索也不足以证明任何具体实现具备或不具备专利新颖性。

本项目更值得验证的贡献是：

- 同一套确定性游戏内核同时支持权威在线对局、隔离多 agent 训练和可追溯的反事实分叉。
- 将玩家的合法信息集明确建模，并自动测试动作提示、错误响应、日志、版本和时序是否泄露隐藏信息。
- 生成可逐步验证的训练样本：精确观察、实际动作、判定版本、终止/截断原因和分支来源。
- 在真实适配器上比较普通状态存储与加密包方案，而非先认定加密更快。

建议至少用两个真实已验证游戏执行同一组实验，记录每步 p50/p95 延迟、吞吐、网络字节、CPU、持久化字节和恢复耗时；再注入重复请求、乱序、并发同版本请求、提交后断连、worker 崩溃及旧包回滚。公平比较必须固定审计保存范围和耐久性承诺。

**最终建议：先用“纯规则内核 + 权威单局事务 + 玩家观察投影”完成可靠基线；训练热路径使用进程内 runner，在线服务可使用 SQL 或持久 actor。加密检查点保留为受控的可选能力。只有基准显示具体瓶颈后，再考虑最小 head + 加密状态包。**
