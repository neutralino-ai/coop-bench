# 架构审阅：一致性、隐藏信息与训练可靠性

日期：2026-09-16。本文是 `stateful-api-design.md` 的深入审阅与故障测试清单，属于设计建议，未表示这些机制已经实现或经过性能验证。官方文档已按本文日期查询。

## 1. 建议结论

**采用同一个确定性规则内核，配两种运行方式：在线服务由服务器维护权威状态；大批量训练由本地 worker 维护独立对局。** 两者使用同一规则、观察投影和终局验证器，只替换存储、调度和传输。

在线首版采用单局事务和持久化存储。单机开发可用 SQLite；多实例服务使用 PostgreSQL。先不让 PostgreSQL、Redis、消息队列各自维护一份可写的“真实状态”。Redis 最初只用于可重建缓存、限流或通知；需要 serverless 时可换成一局一个 Durable Object，保留同一个规则内核。

“服务器不自行管理常驻进程”与“系统不保存状态”是两个不同目标。AWS 明确要求普通 Lambda 不依赖调用之间的本地状态，并建议实现幂等；Cloudflare Durable Objects 则直接把计算与持久状态组合起来。因此，**serverless 完全可以有权威状态**，不需要先采用区块链或把全部状态交给客户端。[AWS 应用设计](https://docs.aws.amazon.com/us_en/lambda/latest/dg/concepts-application-design.html)、[Durable Objects 概览](https://developers.cloudflare.com/durable-objects/)

## 2. 软件设计原则落实到边界

| 原则 | 本项目的具体设计 | 应避免的写法 |
|---|---|---|
| 单一职责 | 规则内核判断动作、状态和结果；运行器决定谁何时被调用；存储层负责提交；传输层负责 HTTP/WS；导出器负责训练格式 | 一个 `step()` 同时读 Redis、调用模型、发消息、改规则和写训练文件 |
| 依赖倒置 | 规则层不导入 PostgreSQL、Redis、HTTP 或模型 SDK；适配器实现稳定协议 | 游戏模块直接访问全局数据库连接 |
| 明确状态机 | 顺序行动、同时提交、机会事件、终局是显式阶段 | 用空的 `activePlayers` 猜测“游戏结束”或“该掷骰子” |
| 最小权限 | 服务器私有状态、玩家观察、研究者审计记录使用不同类型和权限 | 对全量状态删几个字段后返回，或将全部轨迹放进 agent 可读工作区 |
| 单一权威 | 一局有一个提交序列；数据库是当前在线分支的最终依据 | SQL 已提交但 Redis 未更新时仍允许 Redis 接受下一步 |
| 可重现 | 版本固定、随机结果有记录、迁移显式、回放输出可比对 | 更新规则代码后直接用新逻辑重放旧数据 |
| 延迟引入复杂度 | 先做到事务正确和泄漏测试，再依据压测选择缓存、actor 或分片 | 尚无吞吐数据就引入区块链、分布式锁及多套可写状态 |

建议规则内核表达：

```text
GameDefinition: 固定规则、任务与组件版本
GameState:      服务器私有的完整规则状态
Decision:       turn | simultaneous | chance | terminal
Command:        玩家意图，或受信运行器提供的机会结果
Transition:     新状态 + 领域事件 + 新决策 + 规则结果
PlayerView:     某玩家此时可见的观察、提示和决策凭证
```

同时动作应由 `applyJointActions` 或等价的阶段控制处理，不能只靠让多人调用普通 `step` 来模拟。随机性可表达为机会节点，运行器抽样后把实际结果交给内核。OpenSpiel 将 `Game` 与 `State` 分开，并分别提供 joint actions、chance outcomes、玩家 observation 与 information state；这是可借鉴的接口经验，但不意味着它已有本研究清单中所有桌游。[OpenSpiel 概念](https://openspiel.readthedocs.io/en/latest/concepts.html)、[核心 API](https://openspiel.readthedocs.io/en/latest/api_reference.html)

## 3. 先定义必须成立的不变量

1. **唯一后继**：在线权威分支的一个内部版本，只能被一个已提交的转移消费；研究者明确创建的 fork 使用新的 episode ID。
2. **原子提交**：新状态、版本、规则事件、幂等结果和待通知事件共同提交或共同回滚。
3. **幂等效果**：同一座位、同一请求键、同一请求内容最多改变状态一次；重试能取回原始响应。
4. **拒绝不变**：非法动作不能消费牌、资源、随机数、轮次或任何会影响规则的状态。
5. **观察隔离**：玩家能获得的数据、动作说明和错误不能超出规则允许的信息。
6. **阶段隔离**：旧阶段的提交不能进入新阶段；一次同时提交不能改变其他玩家仍未提交时可获得的信息。
7. **确定性**：固定初始快照、规则/组件版本和命令/机会事件，回放得到一致的规则状态及结果。
8. **终局封口**：已终局的 episode 不再接受改变规则状态的动作；终局奖励只结算一次。
9. **数据忠实**：训练样本中的前置观察就是该玩家当时得到的观察，不能混入后来获得的信息。
10. **故障显式**：进程崩溃、超时、资源限制与官方规则失败有不同的记录，不能全部计作模型输局。

前八项应作为存储适配器与游戏适配器的共同契约；第九、十项由运行器和导出器联合保证。

## 4. 在线存储方案与事务设计

### 4.1 首选：PostgreSQL 作为服务权威存储

桌游一次动作通常只更新一局。把该局作为事务边界，可使用 `SELECT ... FOR UPDATE` 锁定 `episodes` 行，再验证和提交；不同对局能并行。要求所有修改这局的路径都遵守相同锁顺序，包括系统超时、同时阶段结算和管理员操作。PostgreSQL 行锁用于阻止同一行的并发冲突修改；如果改用更高隔离级别，仍需处理并完整重试序列化失败。[PostgreSQL 行锁](https://www.postgresql.org/docs/current/explicit-locking.html)、[事务隔离与重试](https://www.postgresql.org/docs/18/transaction-iso.html)

建议提交过程：

```text
验证身份和请求的静态格式
BEGIN
  锁定本 episode，重新确认座位权限/状态
  查 (episode_id, seat_id, idempotency_key)
    已存在且内容摘要一致 -> 返回缓存结果
    已存在且内容不同 -> 冲突
  检查本座位 decision_id / view_revision
  用固定规则版本验证并执行纯状态转移
  写新状态、内部 revision、事件、座位投影和幂等响应
  如有异步通知，写 outbox
COMMIT
发送响应；后台按 outbox 投递通知
```

要求数据库唯一约束兜底幂等键和事件序号。幂等检查在阶段/版本检查之前，否则已成功但响应丢失的请求会被误判为过期。数据库连接断开导致“是否已提交”不明时，客户端仍用原请求键重试；不能生成新键再打一遍。

模型推理、第三方网络调用和长时间等待不放在事务中。规则计算若变得昂贵，先在事务外基于快照计算，再以内部版本进行 CAS 提交；失败时重新读取并计算，不能提交旧结果。

通知不是事务提交的一部分。使用 outbox 将“需要通知”与状态一起落库，再异步发送；收件方按自己的可见事件 ID 去重。这样得到的是持久化的动作效果和可重试的通知，不是对网络“绝对只投递一次”的承诺。[AWS transactional outbox](https://docs.aws.amazon.com/en_en/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)

SQLite 可用于单机同协议实现，但其写入并发能力与 PostgreSQL 行锁不同。不能因为 API 层支持多实例，就假定多个实例共享一个 SQLite 文件的部署方式已经验证。

### 4.2 Redis：可以用，但必须明确损失和恢复语义

Redis 的 `WATCH/MULTI/EXEC` 支持乐观事务；Lua 脚本可以原子执行。它们可实现版本检查、状态替换、幂等记录和事件追加，但要放在同一原子单元，不能只给 `SET state` 加锁。Redis Cluster 中，多键事务/脚本涉及的 key 要位于相同 hash slot，可采用 `episode:{id}:state`、`episode:{id}:requests` 等同一 hash tag。[Redis 事务](https://redis.io/docs/latest/develop/using-commands/transactions/)、[Lua 原子执行](https://redis.io/docs/latest/develop/programmability/eval-intro/)、[Cluster hash slots](https://redis.io/docs/latest/operate/oss_and_stack/management/scaling/)

原子性不等于持久性。Redis 默认 AOF 每秒同步策略在灾难时可能丢失约一秒写入；RDB 是周期快照；复制和持久化还要根据部署配置评估。因此，如果“已确认动作绝不能在恢复后消失”是要求，就不能笼统写一句“用 Redis 所以可靠”。[Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

首版建议 Redis 不承载唯一审计账本。缓存失效后从数据库重建；限流或临时通知丢失不能改变官方胜负。若后续选择 Redis 作训练中的临时权威存储，必须声明：允许损失多少 rollout、故障后如何重启 episode、如何防止残缺轨迹进入训练集。不要在同一步中直接双写 Redis 与 SQL 后假装二者是一个事务。

### 4.3 Durable actor：serverless 的合理演进选项

一局对应一个 Durable Object，可把同局访问聚合在同一对象；独立对局分散到不同对象。SQLite-backed storage 提供持久化，运行时具有处理存储并发的 input/output gates。它避免了自行维护路由到进程的问题，但仍然需要动作幂等、规则版本、隐藏信息过滤及审计导出。[Durable Object 存储](https://developers.cloudflare.com/durable-objects/api/sqlite-storage-api/)

不能将“JavaScript 单线程”或“一个 actor”当成所有异步代码天然无竞态：跨 `await` 的外部 I/O 可以带来交错；应按平台事务约定完成状态读改写，不能在规则临界区调用模型。单局串行是正确性需要，扩容主要通过增加同时进行的对局数，而不是把同一局的关联动作任意并行。

## 5. 隐藏信息：字段过滤之外的泄漏

### 5.1 内部版本不等于玩家版本

例如同时选牌时，A 先秘密提交。若 B 的 `GET` 从 `version=12` 变成 `13`，或 B 提交返回“版本过期”，B 就知道 A 已经提交，哪怕没有任何手牌字段被返回。

因此使用三种不同标识：

- `stateRevision`：服务器内部提交序列，不向玩家默认公开。
- `viewRevision`：该座位可见投影真正变化时递增。
- `decisionId`：该座位当前决策机会的不可猜标识，明确绑定阶段和规则允许的提交。

同一同时阶段按 `(episode, phase, seat)` 保存一次私有提交。是否允许修改、是否公开谁已提交、谁缺席、如何超时，均由游戏规则或显式运行协议决定；不能由请求到达顺序隐式决定。收齐后统一结算与揭示。必要时提交接口始终只返回该玩家自己的收据，再由可见阶段事件通知揭示。

### 5.2 不可见状态等价测试

构造两个局面 `S` 与 `S'`，它们对玩家 P 的规则信息完全相同，只替换 P 不知道的手牌或牌堆。验证 P 的以下接口结果一致：

- 当前 observation、合法动作提示、示例动作、动作 mask；
- 提交前的决策与可见版本、事件游标、等待列表；
- 只由可见信息决定的非法请求错误类别；
- 日志和诊断中提供给玩家的字段。

这不是要求隐藏状态影响的真实游戏结果永远一致：翻牌、命中隐藏目标等合法动作本来就可能揭示信息。约束的是**揭示前不多给信息**。如果某游戏允许尝试一个结果未知的动作，应把未知结果建模为合法游戏反馈，不要用“合法动作列表”提前告诉玩家能否成功。

持续 HTTP 响应大小、事件数量、延迟和频繁轮询也可能成为侧信道。第一版优先消除明确字段/计数/错误泄漏，并记录尚未证明消除的时序信道；高强度对抗评测再考虑固定揭示屏障、消息填充及固定调度节奏，不应无证据声称完全无泄漏。

### 5.3 RNG 必须同时可复现与不可预测

当前草稿 `src/common.ts` 将 SHA-256(seed) 截成 32 位，再运行 Mulberry32。它可用于便利的本地测试，但状态空间只有约 2^32，不能把“seed 不返回”当作对抗性隐藏信息保证。足够多的公开骰子/洗牌结果可能约束甚至枚举内部状态；这是由有限状态和非密码学算法推得的风险，本文未执行恢复攻击。

建议：

1. 在线评测由受信运行器创建高熵私有 episode 随机密钥，使用经过验证的密码学随机实现；安全的密钥、token、opaque ID 不使用游戏用的普通 PRNG。
2. 确定性评测使用固定版本的密码学确定性随机流，或将实际 chance outcomes 保存在私有回放日志。必须保留算法版本、流标识和游标，不能只记一个 seed 名称。
3. 洗牌、骰子、标识符分别使用域分离的流，避免观察 ID 或额外随机调用改变发牌。范围抽样避免取模偏差；Node `crypto.randomInt` 明确提供这一性质，但其直接调用不是可重复 seed 接口。[Node crypto](https://nodejs.org/api/crypto.html)
4. 不向策略透露评测 seed；密码学算法也不能保护一个已经向玩家公开的完整密钥。
5. 游戏规则要求重新洗牌后不能追踪实体时，重新生成对外标识；稳定 opaque ID 虽不含数值，也可能让玩家跨洗牌跟踪牌。

## 6. Bug → 不变量 → 故障测试

| 具体故障 | 应保证的不变量/修复 | 必做测试 |
|---|---|---|
| 已落库但响应丢失，重试又出一次牌 | 幂等效果；缓存原始结果 | 提交后、发响应前断连接，再用相同键重试 |
| 相同幂等键换动作骗取旧结果 | 请求键绑定规范化请求摘要与身份 | 同键不同卡牌/阶段/座位请求必须拒绝或隔离 |
| 两个请求同时消费最后一张牌 | 同局唯一后继 | 并发相同 `decisionId`，只有一个状态效果 |
| 两个并发请求都没查到幂等记录 | 事务锁和唯一约束兜底 | 在幂等读取点制造竞争，验证不会重复写事件 |
| 新状态已写，审计日志未写 | 原子提交 | 在每个写入点故障注入，恢复后要么全有要么全无 |
| 通知先发，事务随后回滚 | 通知只来自已提交 outbox | 提交失败时不能出现对应玩家事件 |
| 重复/乱序 WS 通知改变客户端判断 | 座位事件有独立顺序与去重 | 重放、乱序、漏消息，客户端通过补拉恢复 |
| 只读缓存滞后导致旧动作获准 | 校验永远依据权威状态 | 人为落后缓存，提交不能消费旧 decision |
| actor 在 `await` 之间接受第二个修改 | 临界区遵守存储事务约定 | 在存储或外部 I/O 处插入屏障，发起并发请求 |
| Redis AOF/复制恢复后确认动作消失 | 明确耐久策略或废弃受影响 rollout | 故障恢复后比对最后确认动作，不能静默计作完整轨迹 |
| 非法动作已经抽走一张随机牌 | 拒绝不变 | 对每种非法动作检查状态哈希、RNG 游标和事件不变 |
| 玩家用别人的 `cardId` 查询牌身份 | 对象归属先检查，错误不暴露属性 | 猜测存在/不存在的隐藏 ID，响应不得给出牌值 |
| 同时动作中的先提交信息经版本泄漏 | 私有提交不改其他座位可见版本 | 改变 A 提交时点，B 揭示前观察与合法性保持一致 |
| 旧阶段动作穿过了新阶段 | `decisionId`/phase 绑定 | 延迟旧动作到下一轮，必须拒绝 |
| 系统超时与最后一次提交同时发生 | 确定裁决顺序及单次终局 | 相同逻辑时间的提交/超时竞态可回放，结果不分叉 |
| 卡牌 ID 暴露排序或跨洗牌身份 | 标识符与隐藏属性独立 | 交换隐藏牌属性及重洗，检查公开 ID 可跟踪性 |
| 数量溢出、NaN、重复 JSON 字段产生歧义 | 严格边界解析和规范化 | 巨大整数、额外字段、重复字段、超长消息及非法编码 |
| 完整状态被放进 `info`/错误/调试日志 | 默认拒绝泄漏的投影和分级日志 | 用秘密 canary 值扫描玩家全部输出面 |
| 规则升级后同一记录赢变输 | 固定规则/组件/序列化版本 | 新旧版本并存回放；缺版本明确失败，不能悄悄代替 |
| reducer 与 verifier 共享同一错误 | 独立规则样例与边界断言 | 官方示例、人工小局面和守恒性质，不能只测自己回放自己 |
| 进程预算到期被计作官方失败 | termination 与 truncation 分离 | 外部步数/时间上限只标截断；官方时限按官方规则 |
| 队伍终局，但未行动座位漏奖励 | 每个座位最终轨迹闭合 | 终局发生在 A 行动时，B/C 也收到最终观察和一次奖励 |
| 全知审计字段混入 SFT 上下文 | 玩家视图与审计导出类型隔离 | 训练输入中的 canary 隐藏值扫描必须为零 |
| 同一发牌/fork 出现在训练和测试两边 | 按局面/场景族及 lineage 划分 | 输出分区交集检查，相同父局所有分支归一分区 |
| 拒绝的请求触发无限重试 | 有界重试与明确错误分类 | 永久非法不重试；版本冲突刷新；基础设施故障保持原幂等键 |

这些测试的目标是验证跨边界行为，不是为每个简单 getter 写与实现镜像的测试。

## 7. RLVR/SFT：奖励正确不等于训练正确

### 7.1 分清三种验证

- **动作合法性**：动作是否在当前规则状态成立。
- **终局正确性**：按照固定官方规则或明确变体，是否达成胜利条件。
- **信息合规性**：策略选择动作时是否只使用它当时能知道的信息。

前两项通过同一个程序返回 `true` 并不足以证明规则实现正确。应使用官方示例、手工可算的边界局面、牌/资源守恒和对另一套实现的差分测试（确有独立实现时），防止奖励验证器本身成为可利用的漏洞。

团队 win/loss 是基础结果；得分、合法率、耗时、沟通量作为独立指标。中间 shaping reward、非法动作扣分、协议超时如何处理必须单独版本化，否则模型可能学会优化自造分数而非官方目标。

### 7.2 单个玩家的下一步不是服务器下一步

导出的 transition 应从“玩家 P 的一次决策”连接到“P 的下一次决策或终局观察”，中间可能跨越多个其他玩家动作及机会节点。保存经过的规则步数/折扣约定和事件范围。终局时为所有待闭合轨迹补最终奖励，不能仅给最后行动者。

顺序阶段适合 AEC 风格；真正同时阶段适合 Parallel 风格。不能为了统一调用形式，在同时阶段给后行动者额外观察。PettingZoo 官方明确区分这两类接口，并指出不恰当的同时模型容易引入动作顺序竞态。[PettingZoo AEC](https://pettingzoo.farama.org/main/api/aec/)

外部运行预算、进程中断属于 `truncated`；环境定义内的自然终局属于 `terminated`。如果官方游戏本身有时限，达到该时限可以是规则终局，不能一概称截断。Gymnasium 将二者分开，因为价值函数是否 bootstrap 会受影响。[Gymnasium 时间限制](https://gymnasium.farama.org/main/tutorials/handling_time_limits/)

### 7.3 本地训练与远程在线使用共享内核

训练吞吐可能受逐步 HTTP、JSON 编解码、数据库提交和模型调用主导，具体需要压测；不能预先承诺某个 steps/s。

建议提供：

```text
LocalRunner:      N 个独立 episode → worker pool → 批量策略推理
RemoteRunner:     HTTP/WS → 身份/事务 → 同一个规则内核
TrajectoryWriter: 本地批量落盘或在线事务日志 → 共同导出格式
```

LocalRunner 的内存权威状态仅在本 worker 生命周期内有效，周期快照/终局日志负责恢复和审计；丢失的未完成 episode 显式废弃或恢复，不能伪造完整记录。可信训练进程可直接调用内核；对抗性 agent 仍需隔离在仅能取得 seat observation 的进程/容器，不因为本地快就开放真实状态。

先对同一初始局面和动作流运行两种 runner，确保观察、规则结果、随机事件与数据导出一致；再测试吞吐和恢复。跨局 batch 可以并行，同局关联动作依然遵守规则调度。

## 8. 首版与演进路线

**首版必须完成：**

1. 一个资料完整的官方任务；纯内核及显式决策类型。
2. 按座位观察、私有机会状态、严格动作校验、终局验证。
3. 单一数据库事务、幂等键、版本/decision 检查、确定性回放。
4. 本地 runner 与 HTTP runner 的一致性测试；离线 RLVR/SFT 导出。
5. 上表中的重复提交、崩溃恢复、同时阶段及隐藏信息测试。

**测出真实瓶颈后再加入：**

- 缓存/Redis、批量请求、异步轨迹压缩、对象存储归档；
- 按 episode 分区的 Postgres 或 Durable Objects 部署；
- 分布式 worker 调度、训练分区管理、性能基线；
- 有独立研究目标时才实现客户端加密状态、可验证洗牌或去信任执行。

**重要边界：**加密全量状态可以改善数据保密或构建可携带快照，但它本身不解决“哪个后继是权威”“旧快照能否重放”“两个并发合法动作选哪一个”。这些是状态一致性与协议问题。即使最终采用客户端状态信封，也需要明确可信提交头、分叉政策或共识机制；不能把“密文不可篡改”写成“系统无需管理状态”。
