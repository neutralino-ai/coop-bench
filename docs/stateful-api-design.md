## 0. 结论：采用什么，暂不采用什么

**推荐“共享纯规则内核 + 两种运行器”：在线用有持久状态的权威服务，离线训练用本地批量运行器。** 在线 API 计算实例可以无状态、可以 serverless；对局状态由数据库或持久 actor 保存。按对局扩容，无需先设计区块链。

| 决策 | V2 选择 | 原因 |
|---|---|---|
| 软件组织 | 模块化单体；规则内核与网络、存储、训练导出分开 | 先把十款游戏的共同边界做对，避免过早拆成微服务 |
| 在线权威状态 | 首版 PostgreSQL；本地开发/单机用 SQLite | 一次事务提交局面、动作记录、回执、待发送通知 |
| 同局并发 | 每局串行提交；不同对局并行 | 游戏的一次行动必须只有一个确定结果 |
| Serverless 选项 | 无状态函数 + SQL，或每局一个 Durable Object | 计算弹性和状态持久化可以同时存在 |
| Redis | 首版用于缓存、限流、在线状态和通知加速，非必要依赖 | 不让双写和缓存淘汰决定正式胜负 |
| 密文状态包 | 作为可选检查点/迁移格式；后续比较“密文 + 最小 head”方案 | 它解决携带与保密，不能单独解决旧状态重放与分叉 |
| 批量训练 | 本地多环境 worker 直接调用同一内核 | 训练不必每一步走 HTTP 或写完整 SQL 事务 |
| 去中心化密码协议 | 独立研究方向，当前不进入主线 | 只有“不信任服务器”成为明确目标时才有必要 |

这里的“最好”针对当前需求：可信的环境裁判、不可信或会犯错的玩家 Agent、隐藏信息、多游戏规则复用和可回放训练。若以后要求连运营服务器都不知道手牌，信任模型和实施成本会发生根本变化。

## 1. 现成系统怎么做

| 系统 | 已核实的实现方式 | 对本项目的价值与限制 |
|---|---|---|
| Board Game Arena（BGA） | PHP 游戏逻辑、状态机、数据库、按玩家读取数据、私有通知；每个请求创建新对象，回调间不保存实例字段 | 借鉴服务端权威和按玩家投影。平台在线可玩不等于有开放训练 API，也不等于整个平台开源 |
| boardgame.io | JS/TS 的 moves、phases、turns、playerView、联机与存储接口 | 最接近当前 TS 技术栈；借鉴规则抽象，可作为可替换联机/UI层。项目内仍需审计完整同步载荷、日志、撤销、聊天和存储事务 |
| Tabletop Simulator | 虚拟桌面物理交互与 Lua 脚本 | 适合原型和人工游玩；模组可能只摆组件，不能默认是完整合法动作裁判 |
| VASSAL | 开源 Java 桌游模块平台，模块/组件/指令机制 | 可参考联机命令、记录和回放；每个模块自动化程度不同，不默认具备完整 RL 环境 |
| OpenSpiel | Game/State、玩家观察、信息状态、合法动作、机会节点和算法 | 借鉴研究内核、机会事件和信息边界；现成游戏覆盖需逐项检查 |
| PettingZoo | 多智能体环境接口，AEC 与 Parallel 两类执行模式，API/seed 测试 | 借鉴 Python 训练适配；它定义接口，不会替我们实现这批桌游规则 |

直接来源：[BGA Game.php](https://en.doc.boardgamearena.com/Main_game_logic:_Game.php)、[boardgame.io](https://github.com/boardgameio/boardgame.io)、[TTS 脚本 API](https://api.tabletopsimulator.com/)、[VASSAL 源码](https://github.com/vassalengine/vassal)、[OpenSpiel 概念](https://openspiel.readthedocs.io/en/latest/concepts.html)、[PettingZoo](https://pettingzoo.farama.org/)。更详细的源码位置、许可和复用判断见 [平台架构调研](platform-architecture-survey.md)。

**关键先例：BGA 的请求对象不跨请求保留，局面仍能由数据库持续保存。** 因此“服务计算实例无状态”已经足以支持这类部署，不需要把所有状态都交给玩家。[BGA 官方说明](https://en.doc.boardgamearena.com/Main_game_logic:_Game.php)

不直接把任何一个平台整体当作本项目底座：规则执行、多人 UI、托管服务、训练接口是不同职责。现有代码是否能复用，要核对锁定版本的规则覆盖和代码/组件许可。

## 2. 软件设计原则如何落实

采用“端口与适配器”：规则代码不依赖 HTTP、Redis、数据库或网页，同一内核可以由人类、Agent、测试与批量训练驱动。[Cockburn 原始设计](https://alistair.cockburn.us/hexagonal-architecture)

| 原则 | 具体落点 |
|---|---|
| 单一职责 | 游戏内核判断规则；会话服务处理身份/并发；投影模块控制可见性；奖励策略生成训练信号 |
| 依赖倒置 | 内核不导入服务器、数据库驱动或模型 SDK；外围适配器调用内核 |
| 低耦合、按能力扩展 | 新游戏实现少量稳定接口；不要求所有游戏继承“大而全”的基类 |
| 显式状态机 | 阶段、行动窗口、同时动作、机会事件、终局有明确类型，禁止靠多个互相矛盾的布尔变量拼流程 |
| 一份权威、派生读取 | 服务端局面是权威；玩家观察、缓存、通知、训练导出都是派生结果 |
| 不变量先行 | 明确牌守恒、回合合法、隐藏信息隔离等可自动检查的条件 |
| 小步演进 | 先模块化单体，先一个完整官方场景；压测发现瓶颈再拆服务、换存储 |

模块化单体同样可以部署多个计算实例。先建立稳定边界，再考虑独立服务；这也是单体优先建议背后的工程动机，而非“单体无法扩容”。[Fowler 的讨论](https://martinfowler.com/bliki/MonolithFirst.html)

### 建议模块

- domain/：规则状态、动作、机会事件、结果、规则不变量；每款游戏一个模块。
- application/：对局生命周期、提交动作、同时行动的收集与揭示、身份权限。
- projection/：每个玩家的完整观察、公开/私有事件、可提交动作提示。
- adapters/：HTTP、数据库、持久 actor、本地运行器；不包含牌面规则。
- training/：按玩家轨迹、奖励策略、数据划分、Python 接口适配。
- audit/：回放、规则版本核对、实际下发内容与赛后报告。
- rulepacks/：固定版本的场景及组件数据、来源、校验值与实现范围。

不必一开始把每个目录都发布成独立包或服务。

## 3. 核心架构：一套规则，两种运行方式

~~~mermaid
flowchart TD
  Human[人类或在线 Agent] --> API[HTTP / WebSocket]
  API --> Authority[对局权威服务：鉴权、并发、幂等]
  Authority --> Core[纯规则内核]
  Authority --> Store[(权威状态、记录、回执、outbox)]
  Authority --> View[玩家观察投影]
  View --> Human
  Trainer[可信训练协调器] --> Runner[本地多环境运行器]
  Runner --> Core
  Runner --> View
  Runner --> Checkpoint[检查点与批量轨迹]
  Store --> Export[审计与训练导出]
  Checkpoint --> Export
~~~

### 在线模式

用于人类游玩、外部 Agent、正式评测。策略端只拥有自己的座位凭证；不能读取环境数据库、其他座位、随机状态、回放真值或 fork 接口。

每个 episode 是一个并发与事务边界。可以理解成“每桌一个裁判”，但不要求每桌永久占一个进程：请求到来时从数据库读取；提交后计算实例可退出。

### 批量训练模式

可信协调器在环境 worker 内管理多局内存状态，直接调用相同内核和观察投影；定期写检查点，按批输出轨迹。是否持久化每一步由恢复要求决定，不能将这种低开销设置的故障语义与在线正式评测混同。

策略模型与环境真值仍隔离。训练可以允许树搜索/分叉，但必须明确搜索使用玩家信念、采样局面还是全知状态；全知搜索成绩不能当作受限观察玩家成绩。不同模式共享内核，不意味着可以共享任意权限。

## 4. 内核接口：补齐原设计缺失的语义

旧草稿只有 activePlayers 和 step，容易把同时行动、随机事件、游戏结果与训练截断混在一起。V2 的类型草案在 [design-contracts.ts](../src/design-contracts.ts)；旧 [types.ts](../src/types.ts)仅保留兼容现有辅助函数。

    GameKernel
      initialize(config) -> state
      decision(state) -> turn | simultaneous | chance | terminal
      project(state, viewer) -> GameView
      validateIntent(state, viewer, command) -> admissible / safe rejection
      transition(state, player | joint | chance | system input) -> nextState
      outcome(state) -> official result / null
      checkInvariants(state) -> violations

要求：

1. 内核确定性运行，不读墙上时钟、全局随机数、网络或模型输出。
2. 输入输出可序列化，拒绝动作不改变状态，也不推进随机流。
3. 同时行动先由运行器私下收集，每个座位在该窗口只有一份有效提交，齐备后用一个 joint action 原子结算。已提交信息是否公开由游戏规则决定。
4. 随机事件作为可信运行器提供的 chance input。规则公开的骰子概率、牌组构成等可以向玩家提供；不得泄露依赖服务器秘密状态的条件分布、未揭示抽样或私有随机状态，内部 chance 控制接口不向玩家开放。
5. 随机洗牌、超时事件、系统选择与玩家选择分别记账，不冒充同一类动作。官方时限到期通过受信 system input 驱动内核，带事件 ID、窗口 ID 和逻辑时间；它可能产生官方终局。最后一个玩家动作与到期事件按固定裁决策略提交并记录顺序；运行器的外部时间/步数预算则只影响生命周期截断。
6. 游戏结果可以是胜/负/平、得分或剧情 resolution。不能把每款游戏都强制压成 success:boolean；训练奖励另由版本固定的策略映射。
7. 正式规则、官方随机设置、研究变体使用独立规则包 ID，不能隐式添加“每人先讨论十句”等机制。

“可提交动作”与“知道会成功的动作”要分开。例如猜一张暗牌是合法尝试，即使猜错会失败；若动作列表只提供正确答案，就泄露了秘密。反过来，服务端也不能通过详细错误文本暴露未公开牌值。

## 5. 在线存储选择：SQL、Redis、actor、密文包

| 方案 | 正确性与恢复 | 扩展方式 | 本项目选择 |
|---|---|---|---|
| 进程内 Map | 进程退出即丢失；多实例各自有不同状态 | 需要粘滞路由/额外协调 | 本地测试、可信训练 worker |
| PostgreSQL | 事务可同时提交局面、事件、回执；可用每局行锁 | 多计算实例、按 episode 分区；连接池 | 在线首版默认 |
| SQLite | 事务清晰，单机运维简单；写并发边界不同于 PG | 本地单机，不作为多机共享文件数据库 | 本地开发及小规模原型 |
| Redis | WATCH/Lua 等可做原子操作；持久化和故障转移保证依配置而定 | 分片；一局相关 key 需同一槽或重新设计 | 先做非权威加速 |
| Durable Object | 每个对象有身份与持久存储，适合一局一个逻辑 actor | 不同对象并行；仍需处理异步重入和存储事务 | 可替换 serverless 部署 |
| 全状态密文由客户端携带 | 真实性可验证，旧状态仍可重放；恢复依赖谁保留最新包 | 减少服务端热状态，增加传输/加解密 | 可信离线/显式分叉或后续实验 |
| 密文 + 最小权威 head | 用 CAS 选唯一后继；仍需回执和恢复引用 | 热存储小，计算可无状态 | 有实测需求后再实现 |

依据：[PostgreSQL 行锁](https://www.postgresql.org/docs/current/explicit-locking.html)、[Redis 事务](https://redis.io/docs/latest/develop/using-commands/transactions/)、[Redis 持久化](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)、[Cloudflare Durable Objects](https://developers.cloudflare.com/durable-objects/)。

**Redis 可以当权威存储，但这是带明确耐久性取舍的另一种方案。** 若选择它，局面、版本、幂等回执和日志必须在同一原子边界内更新，明确 AOF/复制/故障转移/淘汰策略及可接受的数据损失。普通分布式锁或“先写 Redis 再写 SQL”不会自动提供这个保证。启用 AOF 并选择每秒 fsync 时有丢失最近写入的窗口；普通 Pub/Sub 也不应承担可靠审计日志职责。[Redis 持久化说明](https://redis.io/docs/latest/operate/oss_and_stack/management/persistence/)

V2 默认用数据库事务保证正确性，Redis 故障最多影响速度或在线提示，不能改变哪一步行动被接受。

## 6. 一次动作怎样可靠提交

推荐首版按 episode 行加锁。SQL 的行锁是数据库中的协调点，不依赖某个 Node 进程的内存锁；请求可以落到任意实例。[PostgreSQL 官方说明](https://www.postgresql.org/docs/current/explicit-locking.html)

    1. 限制请求大小并验证身份，确认座位归属。
    2. 开启事务，锁定该 episode 权威行；重新核验当前座位权限、
       credentialEpoch 和撤销状态，再允许查回执或执行动作。
    3. 查 (episode, seat, credentialEpoch, idempotencyKey) 回执。
       同键同请求 -> 原样返回原回执；同键不同请求 -> 冲突。
    4. 校验该玩家的 decisionToken / observationId。
    5. 校验当前行动窗口和可提交性。
    6. 纯内核执行动作，处理必要的机会/自动阶段并检查不变量。
    7. 生成有权返回的观察，持久化完整响应和关联记录。
    8. 同一事务写 state + revision + command/chance log + receipt + outbox。
    9. COMMIT 成功后才返回结果或发送通知。

- **网络重试**：步骤 3 必须先于过期检查。提交成功但响应丢失后，用相同幂等键拿回原结果，不再出一次牌。
- **幂等键作用域**：绑定对局、真实身份/座位和凭证代际；比较规范化请求内容，不把 JSON 字段顺序差异视为新内容。保留期限覆盖整个对局和约定的重试窗口。
- **同时动作**：部分提交更新内部 pending，不能提前产生对手可见的牌面或全局版本跳变；最后一个提交与 joint 结算处于一个事务内。
- **竞争失败**：不返回未成功提交分支的新手牌、随机结果或下一观察，避免策略试探未来再换动作。
- **通知**：使用 outbox，即事务内写待发事件，提交后投递。投递可重复，消费者按消息 ID 去重；玩家能按自己的游标补拉。不能“先广播，再试图提交数据库”。
- **外部调用**：模型推理和长耗时 I/O 不放在数据库锁内。复杂计算超出短事务预算时，采用读版本、外部纯计算、再 CAS 提交；提交时也核验权限代际与撤销状态，失败结果不发给玩家。
- **故障重试**：死锁/事务中止应有界重试；不能假设设置高隔离级别后就不需要重试。[事务隔离说明](https://www.postgresql.org/docs/current/transaction-iso.html)
- **可恢复性**：幂等回执存完整结果或可重建的精确引用。只存“操作成功”无法在丢包后恢复新密文/观察。

目标是同一幂等请求至多一次改变游戏状态，并能重复读取结果；不承诺网络层“恰好一次送达”。

## 7. 版本与隐藏信息：必须分三种标识

| 标识 | 谁能看 | 作用 |
|---|---|---|
| internalRevision | 权威服务/审计 | 每次内部状态提交的版本与 CAS |
| visibleCursor / view generation | 对应玩家 | 只反映该玩家依法可见的变化，用于增量观察 |
| decisionToken | 对应玩家，内容不透明 | 绑定对局、座位、凭证代际、行动窗口代际和可见观察代际 |

原稿的 expectedVersion 容易被理解为内部全局版本，V2 对外改用 decisionToken。其他玩家进行不可见的秘密提交时，不改变该玩家的 token/游标，也不通过请求冲突暴露该提交。行动窗口关闭并开启新窗口后，旧 token 必须失效，即使画面恰好相同。

token 不是对公开牌面 JSON 求哈希就够了：相同画面可能属于不同回合；小空间的秘密哈希也可被枚举。采用服务端认证的不透明 token，或服务端记录的随机标识。

单局中允许多个玩家当前行动时，先后关系由该游戏规则确定；“当前请求者”也不等于“当前行动者”。断线重连不能因此取得他人的手牌。

### 观察边界的验收条件

构造两个不同真实状态 S、S'，若它们对玩家 p 在规则上不可区分，则服务对 p 的观察、动作提示、公开日志、错误分类和游标变化也应一致，或具有同样的可观察分布。这是信息隔离测试，不只检查 hand 字段。

检查全量同步、初始状态、历史日志、撤销、缓存、debug 接口、错误堆栈、卡牌 ID、消息大小和通知时机。缓存键包含对局、座位、权限代际和可见版本，私有响应禁止公共缓存。

不声称互联网服务能完全消除所有计时/流量侧信道。正式基准记录调度策略，对敏感同时行动统一揭示；更强威胁模型需要消息填充和专门分析。

## 8. API V2：玩家端与管理端分开

| 接口 | 权限 | 说明 |
|---|---|---|
| GET /v1/games | 玩家/研究者 | 规则版本、实现范围、资料来源与可运行状态 |
| GET /v1/games/{id}/scenarios | 玩家/研究者 | 只列明已核验范围；研究任务单独标记 |
| POST /v1/episodes | 协调器 | 创建对局；本身也支持幂等；种子与各座位凭证不混入公共响应 |
| GET /v1/episodes/{id}/observation | 玩家 | 自己的投影、observationId、decisionToken |
| POST /v1/episodes/{id}/commands | 玩家 | 发言、规则提示、出牌或其他动作 |
| GET /v1/episodes/{id}/events?cursor=... | 玩家 | 按玩家游标补拉；不使用内部全局序号 |
| POST /v1/episodes/{id}/cancel | 协调器 | 取消/截断及原因；不冒充官方失败 |
| POST /v1/episodes/{id}/branches | 受信研究者 | 受控分叉，独立 episode、继承数据分区家族 |
| GET /v1/episodes/{id}/audit | 审计员 | 真值和回放信息；不能被活动策略读取 |
| POST /v1/exports | 研究者 | 按用途、版本和数据分区导出 |

提交形状：

    Authorization: Bearer <seat credential>
    Idempotency-Key: <request id>

    {
      "decisionToken": "<opaque token from own observation>",
      "observationId": "<issued observation id>",
      "command": {
        "type": "play_card",
        "args": {"cardId": "<opaque card id>"}
      }
    }

不接受客户端自报的 playerId、分数、成功标记或未签封的游戏状态。具体 URL 可在实现时调整，但权限与语义必须固定。

讨论是规则动作的一部分，受阶段、次数、内容约束和可见范围控制。WebSocket 的普通 chat 广播不能绕过游戏禁言。若自然语言约束难以完全自动判断，应标明语义合规审计层；限制成菜单式沟通可能改变规则，必须作为变体披露。

## 9. 用户提出的分区加密方案：可以怎样做

先分清四个目标：

1. **保密**：别人看不见我的手牌。
2. **防篡改**：玩家不能把手牌改成有利牌。
3. **唯一进程**：旧状态不能生成多个都算正式成绩的未来。
4. **可用与恢复**：最新状态持有者断线，其他玩家仍能继续。

分区加密主要帮助 1，经过认证的加密帮助 2；3 与 4 还需要别的机制。仅把签名放进 JWT 并不会保密；普通多接收人 JWE 也不是自动的按字段权限。[JWE 规范](https://www.rfc-editor.org/rfc/rfc7516)

### 9.1 服务器仍受信任时

最简单的密文方案是：

- 一个只供服务端解封的 authoritative capsule，含完整状态、规则版本、随机状态与局面身份。
- 按各玩家权限重新产生的观察；通过 TLS 交付。需要离线传输时再给玩家观察单独加密。
- 玩家能解密的观察副本不作为权威状态输入。否则持有对称密钥的玩家也能伪造其分区。
- 密文认证绑定 episode、规则版本、分区类型、接收者、期限及必要的代际，防止跨局或跨玩家拼接。
- 密钥托管和轮换独立于游戏随机流。加密 nonce 不用游戏回合号或可回退的伪随机状态生成。
- 玩家始终不持有服务器完整状态密钥；恢复/审计也不能把它作为普通工具输出。

单独给每人发送自己的投影通常更简单。向所有人发送所有秘密的密文会增大带宽和密钥泄漏后的影响范围；除非有具体离线/迁移需求，收益不明显。

### 9.2 为什么完全不记状态会允许回滚和分叉

假设客户端保留合法密文 C17。两个计算实例都没有共享的当前状态记录：

    C17 + 合法动作 A -> 验证成功 -> C18-A
    C17 + 合法动作 B -> 验证成功 -> C18-B

两份结果的密文都真实有效。版本号、过期时间、哈希链、签名都不能告诉第二个实例“第一个请求已经消费过 C17”。短有效期只能缩短重放窗口；唯一一次使用仍需要消费记录。

这不是一个一般性的密码学不可能性证明；它是在“没有可信单一协调者、没有可记忆消费记录的硬件、没有外部一致性账本，普通客户端可复制旧包”的假设下的直接反例。若引入可信客户端、共识账本或硬件单调计数器，状态与信任会转移到那里。

本项目提供 [可运行反例实验](../experiments/state-capsule.test.ts)：篡改检测、跨局绑定、两个合法后继、权威 head 拒绝第二分支及幂等重试，共 8 个断言测试已通过。它验证上述协议区别，不代表已经通过生产加密审计或分布式数据库测试。

### 9.3 折中：密文 + 最小服务端权威记录

可只保留热记录：

    episodeId -> currentRevision, headDigest, checkpointPointer,
                 credentialEpoch, lifecycle, rulesVersion

再保存幂等回执、审计事件以及可恢复的检查点。这比保存全部热状态小，但不是“系统完全无状态”。

**与隐藏同时行动的兼容边界：**全局 capsule/head 默认只由可信协调器携带。若让玩家直接携带当前 head，其他玩家的秘密 pending 提交会使包过期，冲突或换包通知本身就可能泄漏其行动。在线玩家仍只提供自己的 decisionToken，由服务端通过 checkpointPointer 读取当前真值；内部 head 冲突不作为玩家可见错误。不能把一套“全局密文版本检查”直接当作玩家可见版本协议。

先将新密文可靠保存到不可变对象/检查点，再用事务 CAS 更新 head、回执和日志。CAS 失败的对象可回收，不能让一个 head 指向尚未可靠保存的 blob。若最新密文只放在发起者浏览器里，提交后对方断线，服务便没有足够信息恢复。

密文版本绑定和 head 校验通过前不得向策略揭示推演结果。用于训练的合法 fork 则创建明确新分支，记录父检查点和共同数据分区，不伪装成同一正式对局。

## 10. 算去中心化、区块链或创新吗

**服务器仍掌握完整解密密钥并裁决动作时，它是中心化权威、客户端携带状态的设计。** Serverless 是部署方式；区块链涉及节点对历史和顺序达成共识。哈希链让相邻记录可核验，但运营方仍可能重写整段链或给不同观察者提供不同分叉，除非存在独立锚定/见证。

若要求服务器也看不到各人的手牌，仅有“分别加密”通常不够：跨玩家判定、洗牌、发牌和牌堆守恒需要可验证操作、零知识证明、多方计算或可信硬件等额外机制；这些路线各有不同信任和性能取舍。去中心化并不会自动删除状态，往往会把状态与历史复制到更多地方。

宽泛思想已有先例：Shamir、Rivest、Adleman 的早期 [Mental Poker 论文](https://people.csail.mit.edu/rivest/pubs/SRA81.pdf)、[LibTMCG](https://www.nongnu.org/libtmcg/)、[Geometry mental-poker](https://github.com/geometryxyz/mental-poker)都提供了相关线索。因此不把“加密手牌 + 无常驻计算实例”称为新的密码学发明。

**有价值的研究点**可能在组合后的可验证收益：多游戏共用的隐藏信息隔离规范、训练/正式评测的分叉权限语义、可移动检查点、审计一致性，以及更低成本的高吞吐训练。能否称为研究创新需要进一步对比已有工作并实验，而不是仅换一个架构名称。

当前选择：把“密文检查点 + 最小 head”保留为可比较的备选方案，不让它延迟官方规则内核和首个环境落地。完整分析见 [加密状态专题](encrypted-state-analysis.md)。

## 11. 随机、公平与可复现

“种子不公开”不等于不可预测。现有 common.ts 草稿将种子压成 32 位并用 Mulberry32，这只适合离线原型；观察足够输出后可能枚举或推断状态。该函数已注明不用于隐藏信息正式评测。

V2 选择可信运行器中的高熵私有随机密钥，以及版本固定的密码学确定性流；公开种子实验与私有评测明确分开。规则内核只接受已记录的 chance outcome，并验证其属于允许的机会结果。不能把任意外部 chance input 暴露为玩家工具。

具体要求：

- 洗牌、骰子、任务抽取、卡牌不透明 ID、加密 nonce 使用独立域/随机来源。加密密钥与 nonce 尤其不能跟随可分叉的游戏状态重放。
- 整数抽样避免取模偏差；洗牌采用正确的无偏抽样。
- 回放固定规则包、组件数据、引擎构建、随机算法与序列化版本。仅保留一个 seed 不足以跨规则升级复现。
- 保存机会结果供私有回放；对策略只公开规则允许公开的结果。
- 若要验证裁判没有事后换牌，可在开局作带秘密盐的承诺，终局按权限验证。这与多人共同生成随机数是不同机制；后者还要解决最后一人拒绝揭示的问题。
- 固定同一随机轨迹的反事实实验与重新抽样的反事实实验分开标注。
- 不能将原始私有状态哈希当公开承诺：小牌组可能被枚举，应采用隐藏性充分的承诺构造。

## 12. 持久化与审计：记录什么才够

首版采用“当前快照 + 追加命令/机会记录 + 定期检查点”，不急于做完整事件溯源框架。拒绝命令进入独立诊断记录，不改变正式局面序号或随机流。

建议持久化实体：

- episodes：完整真值/状态指针、内部版本、规则包、生命周期、分支父关系。
- seats：身份、角色、凭证哈希、权限代际；完整凭证不写普通日志。
- command_receipts：幂等键、规范化请求摘要、提交结果/精确响应。
- transition_log：接受的命令、机会事件、前后状态验证信息、逻辑序号、服务端时间。
- observations：**实际生成/下发的完整玩家观察**、schema 版本、对应行动窗口与可见事件。
- pending_actions：同时选择的私有提交；可内嵌在 episode，保持同一事务边界。
- outbox：待投递的玩家事件；仅含有权下发的载荷或安全的投影引用。
- checkpoints / exports：恢复及批量导出，分权限存放在对象存储或数据库。

区分“服务端生成了响应”“客户端确认收到”“Agent 以此作为动作输入”。单靠 HTTP 日志无法证明模型实际读过；提交时绑定 observationId，必要时有独立确认，审计保留这个证据边界。

存完整下发内容比仅存摘要更可靠。若改成重建，必须能从检查点、规则/代码/序列化版本和事件逐字恢复；仅有哈希不足以重建训练输入。持久化、备份与导出使用独立访问控制；用于可复现的种子和真值永远不混进玩家提示。

## 13. RLVR、SFT 与审计接口

### RLVR：先定义可验证的结果，再定义奖励

官方结果与训练奖励分开：共同胜负游戏可用终局 1/0；得分游戏、剧情决议、多种退出路径必须单独映射并固定 rewardPolicyVersion。未成功终局、取消或超时截断不自动等于官方失败。

正常用户/协调器取消在训练导出中映射为 terminated=false、truncated=true，并记录 endReason=cancelled；仅在状态和最终观察可可靠恢复时闭合轨迹。损坏或不可重建的取消记录进入实验故障清单，排除出训练 transition，不能补造观察或失败奖励。完整性检查与奖励取值是两项独立验证。

非法命令不改变局面；如何罚分/重试是实验协议，需固定版本和重试预算，防止通过无限试探错误结果探索隐藏状态。奖励塑形单独报告，避免诱导拖延、刷分或利用解析漏洞。

胜负验证器的正确性需要官方示例、边界局面和性质测试支撑。把同一个有 bug 的引擎再次回放只能证明一致，不能单独证明官方规则正确；关键胜负条件尽量用独立不变量或小规模穷举核对。

训练转换按**玩家决策时间**建立：当前该玩家观察、动作、到其下次决策期间的环境步数、下一观察、奖励、终止/截断。终局时为所有玩家收尾，即使最后一次行动不是他们做的。

### SFT：不泄露未来信息

输入仅含当时玩家真正可见的规则、历史和观察，目标是合法动作或规则允许的公开消息。成功轨迹先经回放、信息隔离和规则审计；成功不等于每一步都是好示范。

简短决策摘要可作为自述保存，不声称获得隐藏思维链。赛后全知反思另存，不能拼回行动前输入。失败样本可用于批评/纠错任务，但需要单独的数据任务类型。

同局各玩家、重试、共享发牌、所有派生分支在同一数据分区。根据研究问题额外按场景族/角色组合留出测试集，防止按单条动作随机拆分造成泄漏。

### 用户要求的审计

每局输出：讨论发生的阶段/时间、合法公开内容、逐步动作、每步可见信息、玩家自述依据、程序判定结果，以及单独标注的赛后反思。反思必须区分当时可知与终局后才知道的信息。

## 14. 最重要的 bug 与对应验证

| 故障 | 必须成立的不变量/测试 |
|---|---|
| 请求超时后重试，重复出牌 | 同身份同幂等请求只改变一次局面；提交后丢响应重试得到原回执 |
| 两个实例同时接受旧局面 | 并发测试只能有一个正式后继；同局内部版本单调 |
| 玩家 A 收到 B 的缓存手牌 | 两座位同路径读取，缓存不串用；重连和权限轮换回归 |
| 改密文或拼接其他局分区 | 认证失败；跨 episode、seat、rules、epoch 的替换全部拒绝 |
| 同时动作按提交顺序泄漏 | 两种提交顺序的公开轨迹按规则不可区分；联合结算与顺序无关时结果相同 |
| 合法动作列表给出暗牌答案 | 对玩家不可区分的两个真值，提示与可观察错误等价 |
| 发通知后数据库回滚 | 崩溃注入验证：未提交动作不会成为玩家可见的已完成动作 |
| Redis 淘汰/宕机导致胜负回滚 | 默认架构停 Redis 后真值、回执、审计仍完整 |
| 随机数可预测或失败动作消耗随机流 | 私有强随机来源；拒绝命令前后随机状态一致；域分离测试 |
| 规则升级导致旧轨迹改变 | 固定引擎与规则包回放完全一致；旧局不中途换语义 |
| 发牌/弃牌复制或丢失组件 | 牌/棋子守恒、唯一 ID、资源上下界、非法动作不变性 |
| 无限事件触发、召唤循环或极大输入 | 规则允许循环有明确处理；执行预算耗尽记引擎错误/截断，不伪造败局 |
| 训练输入包含真值/赛后反思 | 数据导出字段白名单与未来信息污染测试 |
| 剧情决议或超时被统一计为输 | 域结果、runner 截断、奖励映射分别测试 |
| 讨论绕过禁言阶段 | 所有交流通道走规则权限；自然语言语义限制另审 |
| 终局后某玩家轨迹未收尾 | 所有玩家都有最终可见观察与终止/截断标记 |

更详细的失败模式、SQL/Redis/actor 风险及官方来源见 [故障与测试审查](architecture-failure-modes.md)。

## 15. 如何验证可扩展，而不是凭感觉选架构

用相同内核、相同局面与动作分布比较：

A. 本地内存 worker（训练基线）
B. 无状态 API + PostgreSQL
C. 每局持久 actor
D. 密文 capsule + 最小 head/回执
E. Redis 权威模式（若未来确有需求）

记录每秒有效动作/完成对局、p50/p95/p99 延迟、CPU、内存、数据库写入、网络字节、每百万有效动作成本、恢复时间、可丢失进度、隐藏信息测试结果和回放一致率。这里没有实测容量或费用，不提供虚构吞吐数字。

密文方案大致将每次上/下行的全状态成本推到 O(S)，S 是状态大小；小动作 + 玩家观察方案约为 O(A + O_p)。若把每回合每个玩家的分区一起广播，费用还随玩家数增加。持久化方案也有快照/日志写成本，必须在同样的耐久性和审计设置下比较。

先测无模型环境步，再测完整 Agent 调用。若时间主要花在模型推理，加密和数据库优化的实际收益可能很小；若做大量快速策略/RL采样，本地批量运行器通常值得首先优化。不同回合制游戏不能仅靠一个示例环境的测试外推容量。

## 16. 实施顺序与本轮交付

1. 锁定一个数据完整的高排名官方场景，写出规则不变量与玩家信息边界。
2. 实现纯内核、完整投影和本地运行器；从固定轨迹验证规则。
3. 实现 SQL 对局权威：事务、幂等、同时行动、恢复、通知 outbox。
4. 接入 Agent 工具与审计，完成协议/泄露/故障注入测试。
5. 扩展游戏适配器及 Python AEC/Parallel 训练接口，按共同契约做一致性测试。
6. 取得压测数据后决定是否增加 actor、Redis 权威模式或 capsule 优化。

**设计轮已做**：调查六类现成系统；分析加密/去中心化方案；增加 V2 TypeScript 契约草案；运行 8 项协议反例测试。后续实现轮已完成本地 SQLite 服务与多个游戏，见[运行接口](runtime-api.md)。

**仍未做**：多机生产部署、PostgreSQL/Redis 接入、分布式密码协议、正式 RL 优化器与吞吐压测。原协议实验的 Map 只模拟串行权威检查；新增 SQLite/HTTP 测试单独覆盖持久化、重试、并发决定与回放，仍不代表部署安全认证或断电测试。

主判断：当前最有价值的工作是让规则裁判可信、玩家信息隔离可验证、轨迹可重放，并让同一内核同时服务在线评测与本地训练。Serverless 可以按这条路线实现；不必以放弃权威状态为代价。
